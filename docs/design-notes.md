# 设计与实现说明

**简体中文** | [English](design-notes.en.md)

本文档面向需要修改本插件的开发者，说明各项设计取舍的依据，以及仅通过阅读代码无法得出的约束。文档中涉及的平台行为与 DSH 行为均经实际验证。

## 运行形态：进程内插件

插件以 DSH 进程内插件的形式运行，而非独立桥接进程。该选择并非实现偏好，而是由 DSH 的鉴权模型决定的。

DSH 的 `/api` 对每个请求强制校验签名 Cookie（`dsh-client-connection` 中的 `requestRejection`：先经过 Host 围栏，再调用 `browserAuth.isAuthenticated`）。该 Cookie 需使用进程启动令牌换取，且按 authority 绑定，外部进程无法获取。因此，任何以独立进程通过 `/api` 连接 DSH 的方案，都必须额外解决一个本不存在的问题。

以内置插件形式运行可省去以下各项：

| 独立进程方案所需 | 插件方案 |
|---|---|
| 获取并维护签名 Cookie | 不需要，直接调用 `ctx.sessionController` |
| 探测 DSH 存活状态、维护断线补投队列 | 不需要，与 DSH 生命周期一致 |
| 单实例锁 | 不需要 |
| MCP 配置（为 agent 提供 QQ 工具） | 不需要，使用 `ctx.tools.register` 注册原生工具 |
| 自建控制台端口并自行管理令牌 | 不需要，复用 DSH 已有的令牌 Cookie 与 Host 围栏 |

其代价是插件代码的改动必须重启进程方可生效。`/restart` 命令即为消除该代价而存在。

## 运行中投递：steer 与 queue

包含工具调用且推理强度为 `max` 的回合可能持续数分钟。在此期间到达的 QQ 消息有两种投递方式：

| 投递方式 | DSH 内部接口 | 落点 | 生效时机 |
|---|---|---|---|
| `steer`（默认） | `agent.steer()` | `next-step` 收件箱 | 当前回合的下一个步骤边界 |
| `queue` | `agent.followup()` | `next-turn` 收件箱 | 当前回合整体结束之后 |

需注意以下三项边界，以避免将 `steer` 理解为中断：

1. **`steer` 不中止当前正在执行的步骤。** 它不会中止该步骤已发出的模型请求。若当前步骤正在执行一个耗时五分钟的工具调用，消息需等待该调用返回。需要立即停止时应使用 `/stop`。
2. **`steer` 不结束回合。** `agent/turn-stopping` 仅在 `next-step` 收件箱为空时结束回合，因此插入的消息会使当前回合继续执行。
3. **`/stop` 不丢弃已插入的消息。** Session Controller 的取消操作携带 `keepInbox: true`，收件箱内容保留，并在取消操作静默后按 FIFO 顺序继续处理。

实现上有两项约束：

- **仅在回合确实处于运行状态时使用 `steer`。** 运行状态通过 `ctx.agents.get(sessionId)?.status` 读取（经 `ctx.get` 惰性获取，服务缺失时返回 `null`，表示状态未知）。会话空闲、会话尚未启动或注册表不可读时，一律回退为 `queue`，因为排队的代价仅为延迟，而误判的代价是投递错误。反向竞态（判定为运行中之后回合恰好结束）由 driver 处理：`send()` 检测到 phase 已 abort 时，将 `steer` 降级为下一回合。
- **带前缀的消息不投递给挂起交互。** `/steer 通过` 的语义是插入该文本，若被解析为审批答复则语义完全相反。处理顺序为命令、挂起交互、prompt，前缀消息跳过第二项。

附带效果：`steer` 到达时回复游标会推进至最新消息，群聊 5 分钟的被动回复窗口因此得到刷新。

## 内嵌键盘

平台唯一可随消息下发的交互面是 `keyboard` 字段。本插件用它承载三类选择：模型、审批与单选题选项。点击以 `INTERACTION_CREATE`（`type=11`）事件返回插件，`data.resolved.button_data` 携带按钮的 `action.data`。

实现中有六项约束：

- **`action.unsupport_tips` 为必填字段。** 官方按钮文档将其标注为必填（低版本客户端提示文案）。缺失该字段并非仅缺少提示，而是导致按钮在部分客户端完全不渲染。
- **`render_data.label` 上限为 10 个字符**，而模型 id 通常超出该限制（`deepseek-v4.1-flash` 为 19 字符）。因此按钮仅显示页码内稳定的编号，实际标识存放于无长度限制的 `action.data`，编号与模型的对应关系由消息正文给出。
- **按钮 payload 使用绝对标识而非位置标识。** 采用 `model|<provider>|<model>` 而非 `model|#<索引>`。模型目录是动态的，若某个提供方中途消失，位置标识会导致整体错位，使用户切换到非预期的模型。
- **按钮点击需单独订阅 Intent。** 网关默认仅订阅 `GROUP_AND_C2C_EVENT (1<<25)`，无法接收 `INTERACTION_CREATE`，需订阅 `INTERACTION (1<<26)`。缺失时表现为键盘可正常下发但点击无响应。
- **键盘仅能挂载于 markdown 消息。** 同一个键盘挂载于 `msg_type: 0` 的纯文本消息时，平台接受请求但不渲染按钮；改为 `msg_type: 2` 后立即生效。因此带键盘的消息强制使用 markdown，`markdownMode` 设置仅作用于不带按钮的消息。
- **点击必须被回应。** 收到 `INTERACTION_CREATE` 后需调用 `PUT /interactions/{interaction_id}`（body 为 `{code}`，取值 0 表示成功、1 表示失败、4 表示无权限）。同一 id 仅能回应一次，超时不补。仅发送消息不构成回应。回应码显示于 QQ 客户端，因此权限不足时应返回 4 而非 0。

**一次点击涉及两个 id，不可混用。** 事件体中的 `d.id` 是互动 id，仅用于 `PUT /interactions/{id}`；被动回复所用的 `event_id` 取自事件最外层的 id（WebSocket 帧自身的 `id`，形如 `INTERACTION_CREATE:<uuid>`）。将互动 id 用作 `msg_id` 会得到 `40034024 请求参数msg_id无效或越权`；将 `d.id` 用作 `event_id` 会得到 `40034025 请求参数event_id无效`。帧 id 仅在传输层可见，因此 `Gateway` 将其作为第三个参数传递至 `normalizeInteraction`，交互对象同时携带 `interactionId` 与 `eventId`。

**被动目标必须携带类型，失效目标必须兜底。** 回复游标由同一会话共享：游标中残留的失效目标会使该会话后续的每次正常回复都尝试以该目标发送并一并失败。因此游标记录 `replyTargetKind: 'message' | 'event'`（旧存档按 message 处理），且平台返回「已过期」或「无效」时一律视为失效目标：先清除，再以主动消息重发一次。

按钮点击作为普通消息处理：先经过准入判断，再以与人工输入完全相同的文本投递给挂起交互注册表。因此解析、重新提示、超时以及与桌面端的竞争均复用同一路径。此外，帧的 `event_id` 本身即是一个被动回复目标，因此回复点击不消耗主动消息额度。

## 平台指令面板

桥接一度自带按钮快捷菜单，现由平台自身的指令面板取代。取舍依据三条：

1. **面板在群聊中同样存在。** 平台更早的「自定义菜单」仅支持单聊，而本部署主要通过群聊使用，单聊专属的入口价值有限。
2. **面板可限定到具体会话。** 安装时使用 `target_type: specific` 并附带 `group_openids` / `user_openids`，只覆盖本桥接已绑定的会话（每个场景至多 20 个），不会改变其他使用者的界面。
3. **面板可跨重启存在。** 面板带 `remark` 标记，平台保存该字段但不展示，因此再次安装时找到的是同一个面板并原地更新，而不是不断新增。

面板不消耗消息额度：点一项只是**把该项的名称填进输入框**，仍需按发送。因此面板项的名称就是命令本身，点一下之后只差一次发送；`/steer` 与 `/queue` 不在其中，因为二者需要携带文本，填进输入框等于让操作者自己把句子写完。

面板是**本构建命令列表的一份副本**，命令列表一变，这份副本就开始说谎 —— 实际发生过：操作者的选择器里始终是 10 条命令，而桥接已经应答 17 条。因此每次启动都会刷新已存在的面板，但**只刷新、不新建**：删除面板是操作者的明确意愿，启动时重建等于悄悄撤销它。安装面板始终是显式动作（`/menu install`，仅 owner），因为它写入的是机器人自身的配置，而非本对话。

## 快捷词与完整匹配

命令可以不带斜杠书写，中文另有 17 个对应词（一词一命令，不设同义词），匹配要求整条消息完全相同且大小写不敏感。

**快捷词是唯一可以用语音触发的命令入口。** 平台把语音转写为文本，因此中文词与命令名都能说出口，而下拉面板无法用语音打开 —— 这是两者的主要区别，也是快捷词保留下来的原因。快捷词同时不引入第二张需要维护的表：英文直接复用命令名本身（`status` 即 `/status`），只有中文需要一张对照表；而**同义词表比命令本身更难记**，因此一个命令只给一个词。

匹配要求整条消息完全相同，所以「任务完成了」不会被当成命令；大小写不敏感，`status`、`Status`、`STATUS` 等价。

## 命令识别越过开头的 @ 提及

平台把提及写进消息正文本身：群里 `@机器人 /usage` 到达时是 `<@ABC> /usage`。命令识别看到的因而是一条以提及开头的消息，`/usage` 不再是命令 —— 这个故障实际发生过。

现在的处理是：识别阶段剥离开头的一个或多个提及，**仅识别阶段**。投递给 agent 的正文保持原样，因为提及是用户写下的内容。

剥离后的副本必须同时用于快捷词查找与随后的斜杠判断。第一版修复只把它用于快捷词查找，单词不是快捷词时又退回原文，而所有斜杠命令都不是快捷词，于是提及被原样放回，`/usage` 依然失效。当时的测试只断言「有消息发出」，失败路径同样会发出消息，因此测试全绿而功能是坏的；现在的测试断言命令自身的输出，并断言提及没有进入该输出。

## 被动回复优先

|  | 主动消息 | 被动消息（携带 `msg_id`） |
|---|---|---|
| 前提条件 | 无，但用户可关闭接收 | 用户刚发送过消息（单聊 60 分钟 / 4 次） |
| 失败方式 | 用户关闭开关后一律失败 | 窗口内稳定送达 |
| 频控 | 20/qpm、1000 条/天/关系 | 不占用主动额度 |

**被动窗口由次数与时间两条规则共同决定，而时间规则无法由本地计数器感知。** 群聊的 `msg_id` 在 5 分钟后失效（单聊为 60 分钟），而一个包含工具调用的长回合可能远超 5 分钟，因此回复生成时目标已失效，平台返回 `msgid已经过期,不能回复`。

本插件因此采取两项措施：

1. **记录回复目标被启用的时刻**（`replyTargetAt`）。超过窗口后不再尝试被动发送，直接使用主动消息，避免发出必然失败的请求并浪费回复额度。
2. **兜底重试**：若仍被平台以「已过期」拒绝，则清除失效目标并以主动消息重试一次。该重试是安全的，因为目标过期即证明消息未送达，不会造成重复发送。

因此**审批与提问提示使用 `deliver`（被动优先、自动降级为主动），而非 `sendActive`**。这两类消息是本桥接中最不容丢失的：一条未能送达的审批会使回合停滞，而操作者在 QQ 侧无法观察到任何异常。同理，所有发送失败均会抛出异常而非静默返回，并记录至 `/status` 的「最近一次发送失败」。

## 出站编码：一条消息一次决定

一条回答使用 markdown 还是纯文本，在**拆分之前决定一次**，随后与该消息的所有分块一同传递。曾按分块各自决定，两者因此可能不一致：纯文本转换会移除决策所依据的特征（表格），于是已经转换过的正文会以 markdown（`msg_type: 2`）发出。

`auto` 的规则是：平台能忠实渲染时使用 markdown。平台支持粗体、斜体、列表、引用与分隔线，但不渲染表格，因此表格是唯一改用纯文本更易读的情形 —— 而纯文本路径会把表格重写为 `· 表头：值` 形式，这条规则才真正成立。（早期版本已如此宣称，但转换器根本没有表格处理：两种编码下表格都只是一行竖线，退回纯文本只让消息的其余部分丢掉了格式。）

带键盘的消息强制使用 markdown：按钮只在 markdown 正文上渲染。因此 `markdownMode` 只作用于不带按钮的消息。

编码决定会留下记录：每次发送记录一次所用编码，退回纯文本时另记原因。否则「那一条为什么是平的」在事后无法回答。

## 表格的识别条件

一个表格只有在**一行单元格之下紧接一行分隔行**时才成立，且两行都必须带竖线。`readTable` 要求候选表头行以 `|` 开头并以 `|` 结尾，下一行为分隔行，且其后至少有一行正文；`canRenderAsMarkdown` 用同一条件判断一段文本是否含表格。

早先的规则只在单行上匹配分隔行，于是 `---`（普通分隔线）也会命中：所有含分隔线的消息 —— 报告类输出大多如此 —— 被判定为含表格并转为纯文本，而这条规则本意要选择的 markdown 路径一次都没有走到。发现它的是那次真机 A/B：两条对照消息的呈现完全相同，而「完全相同」恰恰说明两者走的是同一条路。

## `/restart` 的实现要点

`/restart` 使插件代码的更新与进程恢复无需依赖桌面环境。实现包含以下要点：

1. **`detached: true` 在本机环境中失效。** 实测结果为：`spawn('powershell.exe', ..., { detached: true })` 退出码为 0、无输出、无副作用，且不触发 `error` 事件，重启器完全没有执行，`/restart` 因此仅完成了一次停机。现改为 `cmd /c start "" /min powershell -File <脚本>`：脚本写入 `~/.dsh/dsh-qq-restart.ps1`（将多行带引号的 PowerShell 嵌入 `start` 的参数迟早会引发解析问题，而此处仅需一个路径参数），并且 `start` 会为其创建独立控制台。该独立控制台是必要的：`dsh web` 运行于本进程的控制台，本进程退出时该控制台随之关闭，仍挂载其上的进程会被一并终止。
2. **必须先释放端口。** 启动脚本的判断条件是「3080 端口已有监听则视为服务已运行，仅打开浏览器」。因此插件不直接调用启动器，而是先启动一个 PowerShell，由其轮询至端口不再接受连接后再调用启动器。
3. **确认消息必须先于进程退出发出。** 进程即将退出，仍滞留在发送队列中的消息等同于未发送。因此流程为：`prepare()` 判断是否具备重启条件（不满足时明确拒绝，不使服务停留在无法启动的状态）→ 发送确认消息 → `go()` 写入标记、启动进程、延时 2 秒退出。
4. **新地址必须主动回传。** 每次启动的令牌均不相同，因此旧链接必然返回 404，此为设计使然。`connection.authenticatedUrl()` 是获取本次有效地址的唯一接口。插件在进程退出前将发起者写入 `~/.dsh/dsh-qq-restart.json`，新进程在 QQ 通道恢复 `online` 时将该地址回传至对应会话。标记读取后即删除，因此一次重启恰好产生一条通知。
5. **每个步骤都必须留下记录。** 重启发生在无人值守时，而其两种失败方式（启动器未被执行、启动器已执行但服务未恢复）从 QQ 侧观察完全相同。因此该隐藏 PowerShell 将每一步写入 `~/.dsh/dsh-qq-restart.log`，重启后的通知再将最后两行回传至对话。
6. **重启前必须执行自检。** `/restart` 是加载代码改动的唯一通道，这使存在缺陷的改动可能导致无法恢复。因此在进程交接前，先在子进程中完整 `import()` `lib/index.js` 的依赖图（健康时约 107ms，存在缺陷时返回 `ERR_MODULE_NOT_FOUND` 原文），失败则拒绝重启。使用子进程而非进程内 `import()` 的原因是模块带缓存，而需要捕获的失败类型（语法错误、缺失导出、顶层 await 阻塞）恰好会使加载器一并失效。
7. **回合运行期间需要二次确认。** 重启会连同收件箱一同丢弃正在运行的回合，且不可撤销。回合运行期间执行 `/restart` 将返回说明及 `/restart force` 提示。

## `/usage` 的数据来源

`/usage` 读取 DSH 自身维护的数据，不调用 provider 接口，也不展示无法据以行动的会话统计（例如「本会话 12 轮 86 步」）。

| 文件 | 内容 |
|---|---|
| `~/.dsh/dsh-usage/provider-snapshots.json` | 各 provider 的余额与套餐窗口（百分比及重置时间） |
| `~/.dsh/dsh-usage/usage-ledger.json` | 按天、provider、模型统计的输入、输出、缓存命中 tokens 与花费 |

该设计保证手机端与桌面端显示一致，且桥接不经手任何凭据。两项实现细节：同一账户被两个 provider id 重复报告时仅显示一次（`deepseek` 与 `deepseek-official` 报告同一余额，重复显示会被理解为两个账户）；既无余额、又无套餐窗口、且当日无使用记录的 provider 不予显示。

## 会话与工作区命令

`/sessions` 与 `/workspace` 均采用编号菜单形式，原因是在移动端输入绝对路径与辨认时间戳均不可行。

- `/sessions` 使用标题标识会话（读取桌面侧栏所用的同一 `title` 投影），且不列出已归档会话，因为归档的语义即为「不再显示」。无法获取标题时回退为「短 id · 目录名」，不显示空值，也不生成推测值。
- `/workspace` 列出已登记项目（`workspaceRegistry.list()`，与桌面侧栏数据一致），标记当前设置项，并显示当前会话的工作目录。
- `/new <编号>` 同时完成切换工作区与新建会话。编号无效时整条命令被拒绝，因为部分执行会使用户误以为两项操作均已完成。
- `/new` 不会删除原会话：桥接仅解除绑定，原会话可通过 `/sessions` 与 `/resume` 返回。

## 三项 DSH API 约束

1. **`sessionController.create` 的 `workspaceId` 与 `cwd` 互斥。** 同时传入会抛出 `session.create accepts workspaceId or cwd, not both`。workspace 本身携带规范化路径，注册 workspace 后不应再传入 `cwd`。见 `lib/bridge/session-create.js`。
2. **`sessionController.prompt(request, signal)` 的 `signal` 为必填参数。** 该实现的第一行即调用 `signal.throwIfAborted()`，未传入会得到 `Cannot read properties of undefined (reading 'throwIfAborted')`。插件使用一个与生命周期一致的 `AbortController`，在卸载时调用 `abort()`，同时取消仍在途的投递。
3. **瀑布链按注册顺序执行，通过 `insert:` 加入的插件排在最后。** `approval/request` 与 `user-questions/request` 是 Cordis waterfall：监听器依次获得 `next`，首先返回结果者认领该请求，后续监听器不再获得该请求。将桌面 UI 接入的内置 bundle 注册早于通过 `cordis.patch.yml` 追加的 `dsh-qq`，它在获得请求后转发至浏览器并等待浏览器答复，仅在浏览器拒绝时调用 `next()`。其后果是本插件曾完全未被调用，问题转发与审批转发全部静默失效，且日志中没有任何记录（当时四个提前返回的分支均未记录日志，这是该问题难以定位的原因）。解决方式是在注册时附加 `{ prepend: true }`，将 QQ 侧插入链首，随后立即启动 `next()` 与桌面端并行竞争。见 `lib/bridge/questions.js` 与 `lib/bridge/approvals.js`。

> 每个提前返回的分支都必须记录日志。上述第 3 条长期未被发现，原因是「处理器执行后被拒绝」与「处理器未被执行」在日志中完全一致。

三项约束均已在 mock context 中复刻，任何重新触发它们的改动都会在 `npm test` 阶段失败。
